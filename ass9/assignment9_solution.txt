Q1(a) Test Plan


1) Objective Of Testing
- Validate correctness, reliability, and robustness of the project .
- Verify end-to-end behavior from log generation to ingestion, processing, detection, incident handling, and response execution.
- Detect cross-module behavior gaps in malformed/edge inputs before they cause incident escalation failures.

2) Scope (Modules/Features To Be Tested)

In-scope modules:
- src/log_generators
- src/log_ingestion_service
- src/log_processing_service
- src/detection_service
- src/ml_service
- src/incident_management
- src/response_service
- src/actuator_service
- src/notification_service
- src/auth_service
- src/pipeline_demo_service

In-scope capabilities:
- Raw event intake and validation
- Log normalization and feature extraction
- Hybrid anomaly detection (rule + z-score + ML)
- Incident severity/correlation and response triggering
- Auth flows and role-based session handling
- API contract checks for key service endpoints

Out of scope:
- Production deployment hardening and cloud cost/performance tuning
- Full load/stress benchmarking of all services
- Live third-party notification channel integration

3) Types Of Testing Performed
- Unit Testing:
  - Validator/Normalizer/FeatureExtractor logic
  - Decision engine matrix logic
  - ML scoring and fallback behavior
  - Auth utility/model behavior
- Integration Testing:
  - Processing pipeline end-to-end event handling
  - Detection + ML combined behavior
  - Auth API flow with mocked dependencies and test DB paths
- API Black-box Testing:
  - Auth endpoints (/health, /register, /login, /verify, /logout)
  - Actuator endpoint contracts (defined test suite scenarios)
- Regression Testing:
  - Multi-suite pytest runs for processing, detection, ML, and auth
- Exploratory Negative Testing:
  - Invalid status/timestamp/null message inputs
  - Timeout and invalid credential handling

4) Tools
- Python 3.13
- pytest (automated tests)

5) Entry Criteria
- Codebase cloned and dependencies installed.
- Python environment configured and import path resolved.
- Core service source directories available under src/.
- Test files and pytest available.

6) Exit Criteria
- At least 8 cross-module designed test cases executed.
- Results documented with Actual Output and Pass/Fail status.
- Evidence logs generated and stored in que/evidence.
- At least 3 reproducible defects identified with suggested fixes.

Q2(b) Defect Identification And Analysis (At Least 3)


BUG-DET-001
- Description:
  DecisionEngine uses generic bool() casting for anomaly flags, so string values like "false" are interpreted as True and can generate false anomalies.
- Steps To Reproduce:
  1. Call DecisionEngine.combine([], {"is_anomaly": "false"}, {"is_anomaly": "false"}).
  2. Observe output fields zscore_triggered and ml_triggered.
- Expected vs Actual:
  - Expected: String "false" should be treated as False (or rejected as invalid type).
  - Actual: bool("false") evaluates True, potentially escalating severity to HIGH.
- Severity: HIGH
- Suggested Fix:
  Implement strict boolean parsing/type validation for is_anomaly fields before severity decisions.

Evidence Observed:
- zscore_triggered = true, ml_triggered = true, severity = HIGH

BUG-DET-002
- Description:
  DecisionEngine assumes rule_signals is list-like; malformed input (None/string/int) causes unhandled exceptions.
- Steps To Reproduce:
  1. Call DecisionEngine.combine(None, {}, {}).
  2. Repeat with rule_signals="not-a-list".
- Expected vs Actual:
  - Expected: Invalid rule_signals should be handled gracefully (fallback to empty list or controlled validation error).
  - Actual: TypeError/AttributeError is raised, which can interrupt detection flow.
- Severity: MEDIUM
- Suggested Fix:
  Add input schema validation at DecisionEngine entry and sanitize unsupported types before processing.

Evidence Observed:
- Exception type raised: TypeError

BUG-DET-003
- Description:
  MLClient external response schema is not validated as dict; non-dict JSON can raise uncaught AttributeError.
- Steps To Reproduce:
  1. Mock external ML response where response.json() returns a list (for example: []).
  2. Call MLClient.predict() in external mode.
- Expected vs Actual:
  - Expected: Invalid schema should return controlled error payload (for example invalid_response_schema).
  - Actual: payload.get(...) fails on list and can propagate unhandled exception.
- Severity: HIGH
- Suggested Fix:
  Validate payload type using isinstance(payload, dict) before field extraction and handle schema errors explicitly.

Evidence Observed:
- Exception type raised: AttributeError
